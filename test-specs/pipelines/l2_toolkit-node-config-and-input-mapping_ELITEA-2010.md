## Test Steps

1. Create the GitHub credential + toolkit (`selected_tools: ["search_issues"]`) and an empty pipeline via API, then navigate to `${BASE_URL}/pipelines/all/{pipeline_id}?destTab=configuration&viewMode=owner`.
   - **Verify**: Configuration panel loads; canvas loads past "Preparing the flow editor..." placeholder.
2. In the TOOLS section, click "+ Toolkit" (`[data-testid="agent-add-toolkit-button"]`), type the toolkit's name into the search field (`[data-testid="toolkit-search-input"] input`), and click the matching menu item (`[data-testid="toolkit-menu-item"]`, filtered by visible text).
   - **Verify**: `[data-testid="agent-toolkit-card"]` now shows the toolkit's name in the TOOLS section. **Timing note**: the popper shows a "Loading..." placeholder that can take several seconds to resolve into real `toolkit-menu-item` rows on this environment (the dev project has ~30 pre-existing toolkits) — a fixed short wait (~600ms) is NOT sufficient and produces an empty/stale list; wait explicitly for `[data-testid="toolkit-menu-item"]` to appear (confirmed this session: a 15s explicit wait was needed after a run that failed at 600ms).
3. Click the canvas "+" button (`button.MuiIconButton-colorPrimary`, first match) then click the `Toolkit` menu item (`role=menuitem`, name `Toolkit`, exact).
   - **Verify**: a Toolkit node appears on canvas (`.react-flow__node-toolkit`, `data-id="Toolkit 1"`).
4. Read the Toolkit node's config fields directly from the node body — **no separate click-to-open action is needed**, same always-expanded-inline pattern already confirmed for the MCP node (ELITEA-1954), HITL node (ELITEA-2014/2015), and LLM node (ELITEA-2004 sibling AFS).
   - **Verify**: Trigger, Toolkit, Input, Output, Interrupt before/after, Structured output are all present. **The Tool select and any INPUT MAPPING section are NOT yet present at this point** — they only appear after a Toolkit is actually selected (see step 6) — this differs from a literal reading of the case's step 3, which lists Tool/INPUT MAPPING as always-visible sections; see Coverage Map.
5. Open the node's `Toolkit` select (`#simple-select-Toolkit`) and select the attached toolkit.
   - **Verify**: combobox shows the toolkit's name; the dropdown's `listbox` listed exactly the one attached toolkit.
6. Open the node's `Tool` select (`#simple-select-Tool` — now present, confirmed to only render once a Toolkit is selected) and select `search_issues`.
   - **Verify**: combobox shows `search_issues`; the dropdown listed exactly the toolkit's `selected_tools` (in this session: just `search_issues`, since that's the only tool `selected_tools` named). Immediately after selection, an `INPUT MAPPING (REQUIRED 1)` accordion appears (parameter: `SEARCH QUERY`) alongside `INPUT MAPPING (OPTIONAL 2)` (`MAX COUNT`, `REPO NAME`) — confirmed via a full label-text dump of the node body.
7. In `INPUT MAPPING (REQUIRED 1)`: open the `SEARCH QUERY` row's Type select (positional — first of the 3 duplicated `#simple-select-Type` selects inside this node, DOM-order-confirmed to be the required-section's row) and select `F-String`; fill its Value input with `{input} error`.
   - **Verify**: Type select shows `F-String`; Value input's `input_value()` is `{input} error`.
8. Open the node's `Input` combobox (`#simple-select-Input`) and select `input`; open `Output` (`#simple-select-Output`) and select `messages`.
   - **Verify**: both comboboxes show the selected values. (Dropdown options observed: exactly `input`, `messages` — same as the sibling LLM-node case, confirming this is a pipeline-wide state-variable list, not toolkit-specific.)
9. Click the pipeline's Save button (`[data-testid="agent-save-button"]`).
   - **Verify**: `PUT ${ELITEA_API_BASE}/elitea_core/application/prompt_lib/${PROJECT_ID}/{pipeline_id}` returns `201 Created`; zero console errors and zero failed (≥400) network requests at any point in the flow.
10. Reload the page at the same canonical URL (all query params included — see the ELITEA-1954 AFS's Known Defects entry re: bare `/pipelines/all/{id}` 404ing).
    - **Verify**: after reload, the Toolkit node shows Toolkit=`<toolkit name>`, Tool=`search_issues`, and the `SEARCH QUERY` Input-mapping Value field still reads `{input} error` — all three confirmed persisted this session via direct field re-read (not just a visual screenshot compare).

## Expected Results
- The Toolkit node's config renders inline on the canvas card — no modal, no side panel, no click-to-open action.
- The Tool select and any INPUT MAPPING sections do NOT exist until a Toolkit is selected; they render EMPTY (zero options) if the selected toolkit has no `selected_tools` — this is a real product precondition, not a rendering defect.
- Once a Tool is selected, INPUT MAPPING sections split into REQUIRED N / OPTIONAL N accordions, one row per the tool's actual parameters, each with its own Type (Fixed/F-String/Variable) select and Value field.
- Input/Output comboboxes list the pipeline's current state variables and accept a selection, independent of the tool's own parameter schema (same behavior already confirmed for the MCP node in ELITEA-1954).
- Saving persists everything; a full page reload confirms Toolkit, Tool, and all Input-mapping values survive unchanged.
- No console errors, no failed network requests, at any step.

- No console-error / no-failed-request assertion was in the original case text; added it to step 9 (checked across the whole flow) — *standard practice per this project's `test-case-analysis` skill; zero console errors and zero ≥400 responses were observed across every run this session (including the run that used a toolkit with NO `selected_tools`, which is a legitimate zero-tools state, not an error state).*

## Network Behavior
- `PUT ${ELITEA_API_BASE}/elitea_core/application/prompt_lib/${PROJECT_ID}/{pipeline_id}` — fires on Save click; `201 Created` on success; persists the Toolkit node's Toolkit/Tool/Input/Output/Input-mapping state. Confirmed via live network capture this session, both with and without a Tool selected.
- `GET ${ELITEA_API_BASE}/elitea_core/application/prompt_lib/${PROJECT_ID}/{pipeline_id}` — fires on page load/reload; the reloaded canvas renders from this response.
- The toolkit-attach popper's toolkit list can take multiple seconds to resolve past its "Loading..." state on this environment (see Test Steps step 2 timing note) — no specific request URL was isolated for this (the popper's own network calls weren't distinguishable from the page's other background polling in this session's capture), but the symptom is real and reproducible: an implementer using a short fixed wait after opening the popper will intermittently see zero `toolkit-menu-item` rows.

**None in the Toolkit-node config-and-persistence feature itself.** Once preconditions are correctly satisfied (a toolkit with ≥1 `selected_tools`), all 10 case steps produced the expected result: toolkit attaches to TOOLS, Toolkit node adds cleanly, Toolkit/Tool selects populate and select correctly, INPUT MAPPING sections correctly split into REQUIRED/OPTIONAL with the tool's actual parameters, Type+Value in the required section update correctly (default `Fixed` → `F-String`), Input/Output comboboxes work identically to the LLM node's, Save returns `201`, and Toolkit/Tool/`SEARCH QUERY` value all persist through a full page reload. ## Automation Hints

- Framework: Playwright + pytest, testid-only `LocatorDescriptor` (per `.agents/testing.md`) — **this case requires `add-data-testid` work before implementation**: none of the Toolkit node's interactive fields (Toolkit select, Tool select, per-parameter INPUT MAPPING Type selects, per-parameter INPUT MAPPING Value fields, Input select, Output select) carry a `data-testid` today. See § Concrete Handles for exact recommended names, all gated to `nodeType === "toolkit"` the same way the MCP node's are gated to `"mcp"` — grep `../EliteaUI/src` for the Toolkit node's render function (likely the same `BaseToolNode.jsx` family used by the MCP node, given the near-identical Toolkit/Tool/INPUT-MAPPING shape) to find the exact call site and confirm whether `InputMappingItem.jsx` is already shared between the two node types (if so, wiring the Toolkit node's testids may be a small, low-risk diff reusing the MCP node's already-proven props).
- **Precondition fixture gap**: the existing `github_toolkit` fixture (`automation/fixtures/data_fixtures.py:242`) does NOT set `selected_tools`, so it cannot be reused as-is for this case — a toolkit with no `selected_tools` renders a Toolkit node with NO Tool select at all (confirmed, not a bug). Recommend either a new `github_toolkit_with_selected_tools` fixture or extending `github_toolkit`/`ToolkitAPI.create_github_toolkit()` with an optional `selected_tools: list[str] | None` parameter.
- No existing page object covers the Toolkit node's inline config fields — `automation/pages/pipeline_detail_page.py` has the MCP-node-specific methods from ELITEA-1954 (`mcp_node_toolkit_select`, `get_mcp_node_tool_value`, `fill_mcp_node_input_mapping_value`, etc.) which are STRUCTURALLY very close to what the Toolkit node needs — recommend either parallel `toolkit_node_*` methods/locators, or (if the underlying components turn out to be shared once `add-data-testid` work lands) a shared helper parameterized by node-type prefix. Do not literally reuse the MCP node's `#simple-select-Toolkit`-scoped methods unscoped — this case's node has a DIFFERENT DOM `id` set (`Toolkit`/`Tool` vs the MCP node's own, though the id strings happen to be identical text — always scope to the specific node's `rf__node-*` container to avoid cross-node-type collisions if a pipeline someday has both node types).
- Wait strategy: (1) wait for `[data-testid="toolkit-menu-item"]` to appear (NOT a fixed 500-600ms wait) when attaching a toolkit in TOOLS — confirmed this session that a short fixed wait produces an empty list; (2) wait for the `PUT .../application/prompt_lib/{project}/{pipeline_id}` response (`201`) before reloading/asserting persistence — not a fixed timeout.
- Suggested pytest markers: `@pytest.mark.p1` (case priority `high` → project convention, see Metadata), `@pytest.mark.pipelines`, `@pytest.mark.regression`. Consider also `@pytest.mark.toolkits` given the toolkit-attach precondition, matching how `test_pipeline_mcp_node_change_toolkit_and_tool.py` uses `@pytest.mark.mcp`.
