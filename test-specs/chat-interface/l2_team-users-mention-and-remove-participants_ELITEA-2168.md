**Setup** (not a case step — establishes the precondition): switch to Team project 471; open a genuinely blank conversation (retry-guarded); open "Add users", search+select `Daniyar Chambylov` and `Ihar Bylitski`, click Add; type+send `"setup message"`; wait for the LLM reply and for the participants badge to read `"3"` (owner + 2 seed users). 1. Verify PARTICIPANTS USERS section is visible on the existing/precondition conversation.
   - **Verify**: `ChatPage.is_participants_badge_visible(section="users")` returns `True` (confirmed live: badge showed "3" going into the case's own steps). Unlike ELITEA-2167's brand-new-conversation case, no reverse-masking correction is needed here — the precondition conversation genuinely already has participants.
2. Open the "Add users" modal (`+` → Invite Users) and select **user_1, user_2, user_3, user_4** (Hrach Sargsyan, Levon Dadayan, Mariam Hakobyan, Tatiana Bontsevich, in that order).
   - **Verify**: four chips shown, in selection order (`ChatPage.get_add_users_chip_names()` — confirmed live: `['Hrach Sargsyan', 'Levon Dadayan', 'Mariam Hakobyan', 'Tatiana Bontsevich']`); Add button enabled.
3. Click the **X** on user_4's (Tatiana Bontsevich's) chip to deselect it.
   - **Verify**: user_4's chip disappears; the other three chips (user_1/2/3) remain, in the same order (confirmed live: `['Hrach Sargsyan', 'Levon Dadayan', 'Mariam Hakobyan']`); Add stays enabled (3 selections > 0).
   - **Mechanism (discovered live — no existing page-object method for this)**: each chip is a MUI `Chip` with `data-testid="add-users-chip-{userId}"` on the chip container itself (already exists, ELITEA-2167) plus an **untestid'd** `<svg class="MuiChip-deleteIcon">` nested inside it — clicking that SVG is what removes the chip. See § Concrete Handles for the `testid needed` this requires.
4. Click **Add**; verify user_1/2/3 are added to PARTICIPANTS.
   - **Verify**: modal closes; participants badge reads **"6"** (owner + 2 setup users + 3 newly-added — confirmed live via `chat.wait_for_participants_badge_count("6", section="users")`); popover lists all six by name plus "All users" footer (confirmed live popover text: `"Users@Daniyar Chambylov@Hrach Sargsyan@Ihar Bylitski@Levon Dadayan@Mariam HakobyanTB@Test Bot@All users"`).
   - **Automation gotcha (discovered live, real defect in the naive implementation, not the product)**: `ChatPage.click_add_users_confirm()` unconditionally presses `Escape` first (`dismiss_add_users_dropdown()`) to close a still-open Autocomplete results popper. After a chip is removed via ITS OWN delete icon (§ step 3), no results popper is open any more (it was already dismissed before the delete-icon click) — so that blind `Escape` instead closes the **entire "Add users" dialog**, discarding the pending selection (confirmed live: modal vanished, badge stayed at the pre-existing "3", Add was never actually clicked). The implementer must click `add_users_confirm_button` **directly** (no preceding blind dropdown-dismiss) whenever the immediately-prior action was a chip removal rather than a fresh option selection — see § Automation Hints.
5. Verify the expanded PARTICIPANTS panel's USERS section shows the first 5 avatars and a "+N" indicator for the rest.
   - **Verify**: with 6 total users, exactly 5 avatars render (`[data-testid="chat-participants-users-avatar"]` count == 5, confirmed live) plus a `"+1"` text node (confirmed live, `ExpandedParticipantsList.jsx`'s `usersToDisplay = users.slice(0, componentWidth <= 200 ? 3 : 5)` + `` `+${users.length - usersToDisplay.length}` `` — exact source-confirmed mechanism).
   - **Panel state gotcha (discovered live — testid gap, not a workaround-and-move-on item)**: this view only renders once the Participants panel is **expanded** (collapsed by default). The existing `ChatPage.expand_participants_panel()` (pre-existing raw-JS-heuristic tech debt, `role-overrides.md`-tracked) DID work live this session, but its sibling `collapse_participants_panel()` **failed** (`"Could not find Participants panel collapse button"`) — and once expanded, the COLLAPSED `chat-participants-badge-users` testid this case's later steps (6+) depend on is **not rendered at all** (a completely different component, `ExpandedParticipantsList`, owns the Users section while expanded, and does not carry that testid). A `page.reload()` reliably resets the panel back to collapsed (confirmed live) and is the safe interim workaround, but the correct fix is a real testid on the panel's own collapse/expand `IconButton` (`Participants.jsx`, currently untestid'd) — see § Concrete Handles.
6. Open Invite Users again, select **user_4** (Tatiana Bontsevich) again, then click **Cancel**.
   - **Verify**: modal closes; user_4 is **not** added; badge stays at **"6"** (confirmed live). Also confirms `excludedUserIds` still correctly drops already-added participants (Hrach Sargsyan absent from a fresh search — confirmed live) even after this case's own chip-deselect/re-add churn.
7. Type `'@Hrach Sargsyan hi'` (substituted for the case's literal "@Test Bot hi" — see § Test Data) and send.
   - **Verify**: typing `"@"` in the composer opens a mention popper (`UserMentionList`, distinct component from the participants dropdown) listing every OTHER participant plus "Everyone"; selecting "Hrach Sargsyan" replaces the typed `"@"` with the literal text `"@Hrach Sargsyan "` (confirmed live via `chat.message_input.text_content()`); typing `"hi"` and sending produces **exactly one** new chat-history entry, not two (confirmed live: message count went **2 → 3**, not 2 → 4) — i.e. **no assistant/LLM message is ever created**, matching the case's "no LLM response generated" expectation. Source-confirmed mechanism: `initializeNewMessages()` (`src/common/initializeNewMessages.js`) only appends the user message when `isSendingToUser` is true, skipping `createAssistantMessage()` entirely — this is a structural fact assertable via message count, not a fragile "wait and see nothing appears" timing check.
   - **Not independently assertable in this environment**: the case's own "notification badge appears" expected result describes something visible only to the **mentioned recipient's own session** (a genuinely different logged-in user) — this single-account localhost setup has no second session to observe it from. Flag as a scope note in the AFS, not a failed assertion; the message-count structural check above is the correct single-account proxy for "this went through the to-user path, not the normal LLM path".
8. Click the USERS avatar group to open the dropdown; hover over a specific user (Levon Dadayan); click the delete icon.
   - **Verify**: "Remove user?" confirmation dialog appears (confirmed live, exact text: `"Remove user?Are you sure to remove the Levon Dadayan user from chat?CancelRemove"` — same `Modal.DeleteEntityModal`/`DeleteParticipantButton` component already used for agent-participant removal, `entityType` resolved to `'user'` for `ChatParticipantType.Users`, `DeleteParticipantButton.jsx`). The delete icon itself is the SAME shared testid as agent removal (`chat-participant-remove-button`) — but the row it's hover-scoped within has **no testid at all** for a Users-section row (confirmed live via DOM inspection of `UserMenu.jsx` — unlike `ParticipantItem.jsx`, which DOES carry `chat-participant-row-{uniqueId}` for the Agents/Pipelines/Toolkits/MCP sections). See § Concrete Handles.
9. Click **Remove** in the modal.
   - **Verify**: Levon Dadayan removed from the dropdown AND from PARTICIPANTS — badge goes **6 → 5** (confirmed live via `wait_for_participants_badge_count("5", ...)`); popover text no longer contains "Levon Dadayan" (confirmed live).
10. Hover over another user (Mariam Hakobyan); click delete; click **Cancel**.
    - **Verify**: modal closes; Mariam Hakobyan is **not** removed — badge stays **"5"**, popover still lists her (confirmed live). **Gotcha (discovered live)**: after step 9's removal, a lingering real-mouse `:hover` on the now-gone Levon row can prevent the delete icon from reliably revealing on Mariam's row — `page.mouse.move(0, 0)` (the same residual-hover reset `remove_agent_participant()` already uses) before hovering the next row is required.
11. Click **"All users"** at the bottom of the dropdown; verify `@Everyone` is inserted into the message field.
    - **CONFIRMED PRODUCT DEFECT (novel, filed this session — issue #1119)**: clicking "All users" in the participants dropdown does **NOT** insert any text into the composer (confirmed live, twice, with the click issued both before and after any composer interaction to rule out an ordering artifact: `chat.message_input.text_content()` stayed `''` both times), and a subsequent send goes through the **normal** LLM-response path (message count went 2 → 4, i.e. both a user message and an assistant reply were created) — never the "send to everyone" path. Root-caused via source: the dropdown's footer routes through `ChatBox.jsx`'s `onSelectParticipant`/`NewChat.jsx`'s `onSelectThisParticipant` (which expects a real participant **object** with `.entity_name`), while `DropdownFooter.jsx` passes the **literal string** `'All users'` for this specific item — only the COMPOSER'S OWN typed-`"@"` mention popper (`onSelectUserMention`) has the `if (user.id === '@everyone')` special case that correctly does the text-insertion + `isMentioningEveryone` flip. **Per the interaction-discovery ladder** (`.agents/role-overrides.md`), the SAME "type `@`, then pick Everyone from that list" alternative interaction mode WAS tried and confirmed to work correctly (see step 12) — so this is a real, isolated product defect in the dropdown's OWN "All users" control specifically, not a case-text/discoverability miss.
12. Type `'hi'` and send `'@Everyone hi'`.
    - **As specced by the case (via the dropdown's "All users" click)**: cannot be completed — step 11's defect means no `@Everyone` text is ever present to send. The implementer should still automate the case's INTENDED observable (a `@Everyone`-mentioned message reaches all participants with no LLM response) via the confirmed-working alternate path: type `"@"` in the composer, select **"Everyone"** from `UserMentionList`, type `"hi"`, send. **Verify**: composer becomes `"@Everyone "` (confirmed live); message count goes **2 → 3** (not 2 → 4) after sending — same structural "no assistant message created" proof as step 7, confirming the mention correctly reached the to-everyone path via this route.
    - **Not independently assertable in this environment** (same limitation as step 7): "all participants receive notification" needs a second logged-in session to observe.
