## Test Steps

1. Ensure Context Management + Automatic Summarization are enabled (defensive guard only — confirmed ON by default).
   - **Verify**: `is_context_management_enabled()` returns `True`. (If a prior run left it OFF, `enable_context_management()` — existing method, confirmed working via toggle-autosave live.)
2. Create a new conversation.
   - **Verify**: conversation created; Context Budget panel not yet visible (it only renders after the first message — confirmed live, matches `ChatPage.context_budget_panel`'s docstring).
3. Send an initial message; expand the Participants panel (collapsed by default — confirmed live) and observe the Context Budget panel.
   - **Verify**: `expand_participants_panel()` + `wait_for_context_budget_panel()` (existing `ChatPage` methods — reuse them, do not re-derive; my own quick re-implementation of the panel-expand heuristic in this session did not reproduce the exact working selector on the first try, so trust the merged method over a fresh derivation) make the panel visible; `context_budget_tokens_display`/`get_context_budget_tokens_text()` shows `"N / M tokens"` with `M` equal to the configured Max Context Tokens; `context_budget_messages_count`/`get_context_budget_messages_count()` reads `"1"` (or the correct running count); `context_budget_summaries_count`/`get_context_budget_summaries_count()` reads `"0"`.
4. Send further messages (long/detailed, per the case's own guidance) to progressively raise the token count toward the configured max.
   - **Verify**: `context_budget_tokens_display` count increases monotonically after each send; **confirmed live** that normal chat send/receive (message post → streamed AI response) works correctly and reliably in this environment (verified across 3 real exchanges in this session, ~4-8s per AI response).
5. Continue until the token count reaches the configured max.
   - **Verify**: a warning affordance appears at/near the threshold — **NOT independently confirmed live this session** (my exploration used a 10,000-token default and did not send enough real messages to approach it — sending 15-20+ real AI round trips was out of this session's time budget; this AFS step is a `testid needed`/behavioral gap for the implementer to confirm on first pass, not a defect). Look for the described "warning icon"/color-changed bar around `context_budget_tokens_display`'s parent — no stable handle discovered yet; **testid needed**: `context-budget-warning-icon` and a `data-*` state attribute on the token bar for the yellow/orange threshold state (state-via-attribute, not a state-dependent testid, per `.agents/testing.md` § Locator policy).
6. Send one more message to trigger summarization.
   - **Verify**: **NOT independently confirmed live this session** (same reason as step 5 — reaching a real max-token trigger needs sending past the session's time budget). `testid needed`: a stable handle for the "Summarizing the chat history" in-progress indicator — none found in `ChatPage` (`grep -in summariz automation/pages/chat_page.py` found only unrelated "Summaries" counter references and an unrelated `summaryContainer` folder-accordion CSS class comment). The implementer's first automation pass should locate this indicator live (likely a transient text/spinner near the message list while the summarization LLM call runs) and either reuse an existing generic loading-indicator pattern or request `add-data-testid`.
7. After summarization, verify the Summaries count increments to 1.
   - **Verify**: `context_budget_summaries_count`/`wait_for_context_budget_summaries_count("1")` (existing methods — use the WAIT variant first per its own docstring, which documents an async-update race with the plain getter). **Not independently confirmed live this session** for the same reason as steps 5-6 — the existing testid/method pair is pre-built for exactly this assertion and is the correct handle to use; the implementer's first pass confirms it fires.
8. Verify the token count is reduced/managed after summarization.
   - **Verify**: `context_budget_tokens_display`'s numerator (used tokens) should visibly drop after the Summaries count increments (summarization compacts history into a shorter summary). **Not independently confirmed live this session.**
9. Continue sending messages to trigger a second summarization; verify Summaries count increments again.
   - **Verify**: `wait_for_context_budget_summaries_count("2")`. **Not independently confirmed live this session** — same reason; mechanically identical to step 7 once step 6-8's mechanism is confirmed working.

## Expected Results
- With Context Management + Automatic Summarization enabled, sending messages until the configured Max Context Tokens is reached triggers automatic summarization: a transient "summarizing" indicator appears, the Summaries counter increments (1, then 2 on a second trigger), and the token count is reduced/managed afterward.
- All of this is **plausible and consistent with the app's own UI contract** (the Context Budget panel's Messages/Summaries counters exist specifically to surface this), but steps 5-9's live trigger sequence was not independently observed this session — see § Blocked Steps. Steps 1-4 (defaults, panel visibility, token counter increasing with real sends) ARE confirmed live.

## Known Defects Found During Exploration
- **[CONFIRMED DEFECT, filed]** Issue #1129 — Settings > Memory (`/settings/memory`) numeric fields (Max Context Tokens, Preserve Recent Messages, Target Summary Tokens) do not autosave; typed values are lost on reload. Toggle controls on the same form autosave correctly (isolated via a same-session control experiment: toggle click → `PUT /api/v2/social/author/` fires + persists; numeric field type + blur → zero network calls, value reverts). Root cause traced to source: `useFormikAutoSaveOnBlur` (blur+dirty gated) vs the toggle handlers' direct `onAutoSaveRequested()` call — the three numeric fields' `onChange` handlers never call `onAutoSaveRequested()` and rely entirely on the (apparently non-firing, for these fields) blur path.
- **[NOTE, not filed separately]** The existing (currently `@pytest.mark.skip`-marked) `test_context_management.py::test_context_budget_reflects_profile_max_tokens` navigates to `/settings/personalization`, a route that no longer exists (`SettingsRedirect.jsx` redirects anything not in its `VALID_TABS` list to the default tab; `personalization` isn't in that list). The FEATURE itself is not gone — it lives at `/settings/memory` today. This is implementer-facing dead-code tech debt in `UserProfileSettingsPage.navigate_to_profile()`, not a case-text clarification (the case ELITEA-2218 itself doesn't name a route) — flagged here for whoever eventually revives that test, not filed as a tracker issue.
