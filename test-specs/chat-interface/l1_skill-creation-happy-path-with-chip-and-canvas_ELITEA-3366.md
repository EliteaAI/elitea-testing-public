## Test Steps

1. Enable the Skills Builder module (precondition, not a numbered case step — see § Preconditions), then send the case's literal test message via the main chat composer.
   - **Verify**: the AI invokes the Skills tool without asking a clarifying question. Confirmed live 6/6 runs: the response's "Thought for N secs" accordion shows TWO `chat-answer-model-chip` tool-call entries both reading **"Elitea Skills: post_elitea_core_skills"** (the tool is invoked twice in the same turn — see Network Behavior; not asserted as a defect, just the observed call count), followed immediately by prose text of the shape `Created the skill {Name} with instructions to extract blockers, decisions, and action items from raw standup notes as a bulleted list.` — no interrogative/clarifying sentence anywhere in the response, 6/6.
2. Verify chat response contains a Skill chip.
   - **Verify**: a `[data-testid="generated-entity-chip"]` element renders inside the AI response, below the prose text. Its visible label (`TypographyWithConditionalTooltip` content) is the skill's slugified `name` (e.g. `daily-standup-summarizer`), **NOT** the literal display-name string `"Skill: Daily Standup Summarizer"` the case's Expected Result column implies — see § Known Defects/Clarifications below (case-text drift, not a defect). The chip carries no distinguishing testid identifying it as skill-vs-agent-vs-pipeline-vs-toolkit beyond its icon (`SkillsIcon`, confirmed via `getEntityIcon({entity_type:'skill'})` source read) — scope assertions to "the one `generated-entity-chip` in this message", not to any text match on "Skill:".
3. Click the Skill chip/link.
   - **Verify**: clicking the chip's hover-revealed "Open entity" icon button (`aria-label="Open entity"`, only rendered/visible on `:hover` over the chip — confirmed live, a cold click without a preceding `hover()` times out because the button is present in the DOM but not yet visible) opens the Skill editor as a right-side Canvas panel. URL gains a `?name=<urlencoded original message prefix>` query param (confirmed live: `/app/chat/{id}?name=Create+skill+called+%27Daily+Standup`) — not asserted as load-bearing, just documented so a URL-based wait isn't mistaken for a canvas-ready signal; wait on the canvas's own `skill-name-input-field` instead.
4. Verify Skill fields in Canvas.
   - **Verify**: `skill-name-input-field` input_value equals the slugified name (e.g. `daily-standup-summarizer`); `skill-description-input-field` input_value equals the AI-rephrased description (confirmed live, NOT a byte-identical copy of the test-data description — see § Known Defects/Clarifications); `skill-instructions-editor-content` (CodeMirror, read via `inner_text()` per the `.cm-line` layout gotcha already documented in `test-specs/skills/_surface.md`) contains the exact instructions text byte-for-byte as supplied in the chat message. The canvas's own Save/Discard pair is both present and Save is `disabled` (no local edits made) — confirmed live every run.
5. Open the conversation's participant list.
   - **Verify**: the just-created Skill is **not** present as a chat participant. Confirmed BOTH live (no `chat-skill-panel`/skill-participant UI anywhere in the composer or an expanded Participants panel across any of the 6 runs) and via source read: `GeneratedEntityChip.jsx`'s `onEntityCreated` handler (`ChatBox.jsx`) for `entity_type === 'skill'` calls **only** `onShowSkillEditor?.(participant)` (`useEditSkill.hooks.js`) — this sets local React state (`setEditingSkill`) and a nav-blocking flag; it never calls `addNewParticipants`/any participant-mutation hook, unlike the agent-creation flow's `useAgentCreation.js` (ELITEA-2166's documented contrast). There is no participants-badge element to open at all for a conversation holding exactly one message and zero participants (same "nothing renders for a zero-participant conversation" pattern ELITEA-2166 already documented) — the absence of any skill-participant UI, cross-checked against the source's one-call-site handler, is the pass signal; there's no "empty participants panel" widget to click open.

## Known Defects Found During Exploration

No product defects found. Two case-text/live-product divergences, both **CLARIFICATIONS** (reverse-masking guard — the live product is correct; the case's Expected Result wording is imprecise), not filed as `bug` issues per the project's light-dedup bug-filing policy (these are wording-precision notes, not defects):

- **Chip label format**: the case's step-2 Expected Result says `A "Skill: Daily Standup Summarizer" chip/link is displayed` — live, the chip's visible label is the skill's own slugified `name` field (e.g. `daily-standup-summarizer`), with NO `"Skill: "` prefix and no title-case/spaced display name. Confirmed via 6/6 live runs and source read (`GeneratedEntityChip.jsx`'s `label={entity.entity_name}` — a plain pass-through of whatever the backend returns as the created entity's name, no prefix logic anywhere in the component). Automation should assert the chip's label equals the actual created skill's `name` (read via `SkillAPI.list_skills()` or the canvas's own `skill-name-input-field` once opened), never the literal case-text string.
- **Description-field rephrasing**: the case's Test Data table supplies `Description: Summarizes daily standup notes into action items` verbatim, and step-4's Expected Result implies an exact-match canvas field. Live, the AI tool call stores a SIMILAR but non-identical, model-rephrased description (e.g. observed live: `"Summarizes daily standup notes by extracting blockers, decisions, and action items."` vs the supplied `"Summarizes daily standup notes into action items"`) — the Skills-creation tool does not do verbatim field passthrough for `description` the way it does for `instructions` (Instructions matched byte-for-byte in all 6 runs; Description never did). Automation should assert the Description field is **non-empty and topically consistent** (e.g. contains "standup" and "action items"/"blockers"), not an exact string match — matches the project's own non-determinism handling precedent for AI-generated content (`test-specs/chat-interface/_surface.md`'s "AI-generated table content is non-deterministic" entry).

Neither divergence blocks automation or constitutes a FAIL per the case's own Pass/Fail criteria (skill WAS created with substantively-correct fields; chip WAS displayed and functional; no clarifying question; Canvas opened with accurate — if rephrased — content; skill was NOT auto-added to participants).

## Automation Hints
- Framework: Playwright + pytest, ladder locators (`.agents/testing.md`).
- Page object: this case needs page-object methods for (a) the Skills Builder module toggle flow (reuse existing `ChatPage.click_module_toggle("skill_builder")` — BUT see the toast-wait caveat below), (b) reading/clicking the `generated-entity-chip`'s "Open entity" button, and (c) the Skill editor canvas's field getters. Recommend extending `ChatPage` with `open_generated_entity_chip(entity_type="skill")` (hover + click the "Open entity" button, scoped to the LAST message to avoid ambiguity if a conversation ever holds more than one) rather than a brand-new page class — the canvas itself reuses `SkillFormPage`'s exact field testids (`skill-name-input-field` etc.), so once the canvas is open, compose with `SkillFormPage`'s existing getters (`get_name()`/`get_description()`/`get_instructions()` if they exist, or add them) instead of duplicating field-read logic.
- **`click_module_toggle("skill_builder")` toast-wait caveat — verify before reuse.** `ChatPage.click_module_toggle()` (existing, chat_page.py:3932) waits for a `"Modules configuration updated"` toast after the PUT. This AFS's own exploration did not independently verify whether `skill_builder` is one of the toggles that SKIPS the toast (like `project_context_builder`, per the existing `ensure_module_toggle_checked()` docstring note at chat_page.py:3967) — the scratch-script exploration used a raw `.click()` + fixed wait, not the page-object method, so this wasn't exercised. **Implementer: try `click_module_toggle("skill_builder")` first; if it hangs on the toast wait, switch to `ensure_module_toggle_checked("skill_builder")` instead** (same pattern ELITEA-3254's implementer note already documents for `project_context_builder` — plausible the same no-toast behavior applies to its sibling `skill_builder`, added in the same product change, but NOT independently confirmed this pass).
- Step 1's "no clarifying question" assertion: assert on the STRUCTURAL tool-call signal (2× `chat-answer-model-chip` reading `"Elitea Skills: post_elitea_core_skills"`) per Axis 2, not a text-absence check on the prose — more robust against wording changes.
- Wait strategy: use `wait_for_ai_response()`/`wait_for_message_content_stable()` (existing `ChatPage` methods, same pattern as every other AI-generated-content case in this suite) rather than a fixed sleep — this flow's live response time was consistently 8–10s across all 6 runs ("Thought for N secs" labels observed: 8, 8, 9, 10, 8, 8).
- Skill-name uniqueness: see § Test Data's `generate-per-test` note — suffix the test-data display name with a per-run unique token to avoid slug collisions on repeated runs without full cleanup.
