# Test Case: Context Management – Global Setting Enabled, Auto-Summarization Disabled – Verify No Summarization Occurs When Tokens Exceed Max Limit

## Metadata
- **TMS ID**: ELITEA-2217
- **Linked Story**: none (case `requirements: []`)
- **Priority**: l3 (case priority: medium)
- **Environment Explored**: local (`http://localhost:5173`, `EliteaAI/EliteaUI` on `automation/testids`, DEV backend)
- **User set**: `${TEST_USER}` — on localhost, `auth_state`/`VITE_DEV_TOKEN` skips explicit Keycloak login (dev-token user renders as "Test Bot"/"TB")
- **Analyst**: qa-engineer (agent)
- **Status**: **ready-for-automation** — case executed end-to-end live via Playwright MCP against `http://localhost:5173`. Every step's expected result was reproduced exactly as the case describes: with Context Management ON and Automatic Summarization OFF, sending long messages past a low per-conversation Max Context Tokens threshold drove the token count/percentage past 100% and surfaced the high-utilization warning icon, while the Summaries counter stayed at `0` throughout, no "Summarizing the chat history" indicator ever appeared, and the "Edit context settings" modal confirmed Summaries: 0 + its own summarization toggle unchecked. **One CONFIRMED product defect filed (issue #1605)**, non-blocking (documented workaround exists) — see § Known Defects.

## Preconditions
- User is logged in to the Elitea platform (`${TEST_USER}` / dev-auth on localhost).
- Context Management enabled AND Automatic Summarization disabled in Settings > Memory (`/settings/memory` — same relocation from the case's "Settings > user profile > Personalization" wording already tracked by EliteaAI/elitea-testing-public#1238 via the ELITEA-2218/2216 AFSs; not re-filed here).
- **Confirmed live account default**: BOTH toggles are ON for a fresh session (`context_management_toggle` checked, `automatic_summarization_toggle` checked). This case is the one in the {2216, 2217, 2218} family that must actively flip Automatic Summarization OFF (Context Management itself stays ON) — unlike ELITEA-2218 (both ON, no toggle needed) and ELITEA-2216 (Context Management OFF).

## Test Steps

1. Enable 'Enable context management for new conversations', disable 'Enable automatic summarization' in Settings.
   - **Verify**: `UserProfileSettingsPage.enable_context_management()` (defensive guard — confirmed ON by default) + `disable_automatic_summarization()` (existing method, confirmed live this session: click → `PUT /api/v2/social/author/` → 200, toggle reads unchecked on reload). Both pre-existing `UserProfileSettingsPage` methods/testids (`context-management-toggle`, `automatic-summarization-toggle`) — no new testid needed for this step.
2. Create a new conversation.
   - **Verify**: conversation opens (`/chat/{id}` after the first message, same lazily-created-URL behavior documented by ELITEA-2216). Context Budget panel is not mounted before any message (pre-existing chat-composer mechanism, unrelated to this case's scope — cross-referenced from ELITEA-2216/2218).
3. Send an initial message; expand the Participants panel; observe Context Budget shows fresh counters.
   - **Verify — confirmed live**: `expand_participants_panel_via_toggle()` (ELITEA-2168's testid-backed method, preferred over the legacy JS-heuristic `expand_participants_panel()` per ELITEA-2216's precedent) + `wait_for_context_budget_panel()` make the panel visible. `context_budget_messages_count` reads `"2"` after the first user+AI round-trip (same +2-per-exchange pattern documented by ELITEA-2218 — NOT `"0"`/`"1"`), `context_budget_summaries_count` reads `"0"`. Live observed: `"127 / 6 400 tokens"`, `"2%"` at this point (before any threshold override).
4. Send messages until token count exceeds max (>64000, i.e. whatever threshold is actually configured).
   - **Verify — CORE ASSERTION, confirmed live**: after configuring a low per-conversation threshold (`context_modal_max_tokens_input` = `5000` in this session, via `context-budget-edit-button` → dialog → Save, see § Test Data), sending 4 further long-prompt exchanges drove `context_budget_tokens_display` from `"127 / 5 000 tokens"` (`2%`, `context_budget_percentage`) monotonically upward: `1 090` (22%) → `2 206` (44%) → `3 631` (73%) → `5 301 / 5 000` (**106%**). `context_budget_warning_icon` (`is_context_budget_warning_visible()`) was ABSENT below 100% and PRESENT once utilization crossed it — confirmed via a live poll after each send, exactly matching the mechanism ELITEA-2218 documented (`ContextBudgetProgress.jsx`, `isHighUtilization` at `HIGH_UTILIZATION_THRESHOLD: 1`, i.e. 100%).
5. Verify Summaries count remains at 0 throughout.
   - **Verify — CORE ASSERTION, confirmed live**: `context_budget_summaries_count` (`get_context_budget_summaries_count()`) read `"0"` after EVERY send in the sequence above (checked at each of the 5 exchanges, not just the final one) — never incremented, even at 106% utilization with the warning icon visible. This is the case's central negative claim and it holds exactly as written.
6. Verify no 'Summarizing the chat history' indicator appears.
   - **Verify — CORE ASSERTION, confirmed live**: polled `chat.answer_model_chip` (existing ELITEA-2218 handle, testid `chat-answer-model-chip`) after every one of the 5 sends — every chip read the plain model name (`"Anthropic Claude 4.5 Sonnet"`); none ever read "Summarizing the chat history" (`chips.some(c => c.includes('Summariz'))` was `false` across the full sequence, checked via a live JS query on the collected chip texts). Confirms the summarization sub-step (which reuses `chat-answer-model-chip` per ELITEA-2218's source-level finding) genuinely never fires when Automatic Summarization is off.
7. Open Context Management modal; verify Summaries shows 0; auto-summarization toggle is OFF.
   - **Verify — confirmed live**: opened the SAME per-conversation "Edit context settings" dialog (`ContextStrategyModalContent`, `context-budget-edit-button`) used by ELITEA-2216/2218 — this is the modal the case's "Context Management modal" wording refers to (there is no separate, distinct "Context Management modal"; the global Settings > Memory page and this per-conversation dialog are the two places context-management state is surfaced, and the dialog is the one directly reachable from the chat screen where the case's Steps 3-6 already are). Confirmed: dialog body's Summaries stat reads `"0"`; Tokens stat (`context-modal-stat-tokens`) reads `"5 301 / 5 000"`, percentage (`context-modal-stat-percentage`) reads `"106%"`. **[Amended fix-round-1, ELITEA-2217/PR #1606]** At analysis time the Summaries stat was read via the shared `context-budget-summaries-count` testid (also used by the always-mounted sidebar panel per ELITEA-2216) — the implementer's live run then found this shared testid unreliable *specifically for this modal read*: the dialog is a MUI Portal (mounts to `document.body` after the sidebar's node), so a `.first` read against the shared testid from inside the open dialog resolved to the **sidebar's** copy, not the dialog's own, and was not actually proving the modal's Summaries value. Fixed by adding an optional `testId` prop to `SummaryDetailsButton.jsx` (sidebar's default unchanged) and wiring the modal's own `ContextBudgetStats.jsx` call site to a new, dialog-unique testid — see § Concrete Handles. The modal-own read (`context-modal-stat-summaries`) is now what step 7's assertion uses; the old shared-testid read stays only as a `count()==1` regression guard against the hardcoded/shared shape recurring. **The dialog's OWN "Enable automatic summarization" switch (`ContextStrategySummarization.jsx`) is unchecked, matching the global OFF state — confirmed via a live DOM query (`input[type="checkbox"]` inside the dialog, second occurrence, `.checked === false`) — but this switch carries NO `data-testid` anywhere in the dialog (confirmed both via source read and a live `querySelectorAll('[data-testid]')` sweep of the open dialog — zero hits for any summarization-toggle testid).** `testid needed: context-modal-summarization-toggle` — see § Concrete Handles.

## Expected Results
- With Context Management ON and Automatic Summarization OFF, sending messages past the configured Max Context Tokens threshold drives the token count and percentage past 100% and surfaces the high-utilization warning icon exactly as when Automatic Summarization is ON (ELITEA-2218) — but NO summarization occurs: the Summaries counter stays at `0` throughout, no "Summarizing the chat history" indicator ever appears, and the "Edit context settings" modal confirms both the `0` Summaries count and the summarization toggle reading OFF. Token usage is tracked (unlike ELITEA-2216's fully-disabled case, where the widget stays at all-zero regardless of usage) but never triggers the summarization mechanism. Confirmed live, exactly as the case describes.

### Axis 2 — Analyst additions

- **Discovered and filed a non-blocking product defect (#1605)** while configuring the low per-conversation threshold needed to reach step 4 in reasonable time: with Automatic Summarization globally OFF, the "Edit context settings" dialog's Target Summary Tokens field is correctly disabled, but its stale value still participates in cross-field validation against a new Max Context Tokens value, permanently blocking Save unless the new Max Context Tokens is ≥ the frozen Target Summary Tokens value — *added: without isolating this (confirmed live by proving Save re-enables the instant a high-enough value is entered), the natural read would have been "the modal is just broken when summarization is off," which would have sent the implementer down the wrong path (e.g. assuming the whole per-conversation-modal technique from ELITEA-2218 is unusable for this case) instead of the narrow, documented workaround.*
- Confirmed the modal's own "Enable automatic summarization" switch (`ContextStrategySummarization.jsx`) mirrors the global Settings > Memory toggle's checked state and disables its own child fields (Summarization Instructions, Target Summary Tokens) when unchecked — *added: this is the SAME field that gates #1605's validation bug, so the implementer needs to understand this coupling, not just the workaround value.*
- Verified the Messages/Summaries/Tokens counters behave identically to ELITEA-2218's fully-enabled case UNTIL the actual summarization trigger point — i.e. Context Management being ON is what drives token tracking, independent of whether Automatic Summarization is also ON — *added: pins down that this case is genuinely testing the auto-summarization flag in isolation, not a degraded/different tracking mechanism; the ELITEA-2216 (Context Management OFF) case is the one where tracking itself stops, a different axis entirely.*
- Console checked throughout (Settings > Memory page, chat composer, mid-generation ×5, modal) — 0 errors at every point.

## Known Defects Found During Exploration
- **[CONFIRMED DEFECT, filed]** Issue #1605 — "Edit context settings" dialog: Save is blocked by the disabled Target Summary Tokens field's stale value when Automatic Summarization is globally OFF. Cross-field validation runs against a field the user cannot edit (it's correctly disabled), so a new Max Context Tokens value below the frozen Target Summary Tokens value renders `.Mui-error` on the Max Context Tokens field and permanently disables Save — confirmed live: Save re-enables the instant a Max Context Tokens value ≥ the frozen Target Summary Tokens value is entered. **Does NOT block this case** — a documented workaround exists (choose Max Context Tokens ≥ the live Target Summary Tokens value, or configure the desired low pair while Automatic Summarization is still ON, then disable it afterward). Distinct from #1129 (global Settings page's numeric fields don't autosave at all) — different object, different trigger; filed as a sibling, cross-referenced, not a duplicate.
