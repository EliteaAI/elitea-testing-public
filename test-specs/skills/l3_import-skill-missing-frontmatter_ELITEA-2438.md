# Test Case: Import Skill with missing required frontmatter shows validation error

## Metadata
- **TMS ID**: ELITEA-2438
- **Linked Story**: none
- **Priority**: l3 (medium, per case)
- **Environment Explored**: local (`http://localhost:5173`, EliteaUI `automation/testids` branch → DEV backend, project `Private` / id `399`)
- **User set**: `${TEST_USER}` (localhost `auth_state`/`VITE_DEV_TOKEN` bypass)
- **Analyst**: qa-engineer (Sage), analyst slot
- **Status**: ready-for-automation

## Preconditions
- User is logged in (on localhost, `auth_state` fixture skips login via `VITE_DEV_TOKEN`).
- A project is selected/accessible (`Private`, id `399` in this run).
- Skills → Import feature is available from the Skills list page toolbar
  (`SkillsListPage.import_button`, testid `skills-import-button`, already
  page-object-backed — see `l3_import_skill_base_version_ELITEA-1737.md`).

## Test Data

### generate-per-test (static fixture file, no live entity created)
- A `.md` file whose YAML frontmatter is **missing the `name` field** but
  otherwise well-formed (has `description`, `tags`), e.g.:
  ```
  ---
  description: "A skill missing the required name field"
  tags:
    - regression
  ---
  You are a test skill body used to verify the missing-frontmatter
  validation error (ELITEA-2438).
  ```
- This file can be a **static repo fixture** (e.g.
  `test-data/skills/missing-name-frontmatter.md`) — unlike ELITEA-1737/1738
  it does not need to be generated by exporting a live skill first, since
  the point of the case is exactly that the file is invalid and no entity
  is ever created from it. No cleanup needed (no skill, no version, no
  server-side object of any kind is created by this flow).

## Test Steps

1. Navigate to `${BASE_URL}/skills/all`.
   - **Verify**: page loads, Import button visible in the toolbar, skill
     count in the page-header user-stats block reads some baseline N
     (used for the before/after comparison in step 4).
2. Click the **Import** button, and in the resulting native file chooser
   select the fixture `.md` file described above (frontmatter has
   `description`/`tags` but no `name` key).
   - **Verify**: the native file chooser opens
     (`page.expect_file_chooser()`).
3. Complete the upload (`file_chooser.set_files(path)`).
   - **Verify**: **no "Import parameters" dialog appears** (this is the
     key divergence from the valid-file path in ELITEA-1737/1738 — see
     Known Defects/clarification note below, this is NOT a bug). Instead,
     an error toast (`Alert`, `data-testid="toast-alert"`,
     `data-severity="error"`) appears within ~1s containing the message
     (`data-testid="toast-message"`):
     `The [<filename>.md] is missing required metadata: frontmatter must
     contain "name" and "description".`
   - The message names the actual uploaded filename and both required
     field names verbatim — this satisfies the case's "user-friendly
     validation error indicating the missing field" pass criterion.
4. Verify no Skill is created:
   - **UI signal**: the page-header user-stats "Skills:" count is
     unchanged vs. the step-1 baseline (confirmed live in this run: `11`
     before and after — no re-render/refetch of the skills list occurred
     at all, since the whole validation happens client-side before any
     network call).
   - **API signal (stronger, implementer should prefer this)**:
     `SkillAPI.list_skills()` (`automation/api/client.py:1407`) called
     before and after the failed import returns the same skill count /
     same set of skill IDs — no new skill entity exists.
   - **Network signal**: no `POST .../elitea_core/skill_import/prompt_lib/{project_id}`
     request fires at all (confirmed live via
     `browser_network_requests` filtered on `skill_import` — zero
     matches). The validation in
     `useSkillImport.hooks.js::stageFile()` runs entirely client-side
     (parses the uploaded file's frontmatter via
     `parseMdFrontmatter()` and checks `!frontmatter?.name ||
     !frontmatter?.description` before ever calling the import mutation)
     — this is a stronger and faster assertion path than waiting on "no
     new row" in the UI.

## Expected Results
- The native file chooser opens and accepts the `.md` upload.
- No "Import parameters" preview dialog appears (upload is rejected before
  reaching that stage).
- An error toast appears with a user-friendly message naming the uploaded
  filename and stating that `"name"` and `"description"` are required
  frontmatter fields.
- No Skill entity is created (skill count and skill ID set are unchanged;
  no `skill_import` network request fires at all).
- No console errors during the flow.

## Network Behavior
- **No** `POST /elitea_core/skill_import/prompt_lib/{project_id}` fires —
  confirmed live via `browser_network_requests` filtered on
  `skill_import`, zero matches after the upload + error toast.
- The only network calls observed around the upload were the page's
  pre-existing list/tags fetches from initial page load
  (`GET /elitea_core/skills/prompt_lib/399?...`,
  `GET /elitea_core/tags/prompt_lib/399?...`), both already resolved
  before the file was selected — nothing new fires as a result of the
  invalid upload.
- Validation is 100% client-side: `useSkillImport.hooks.js::stageFile()`
  reads the file via `file.text()`, parses frontmatter via
  `parseMdFrontmatter()`, and calls `toastError(...)` + returns before
  `setPending(...)` / the import mutation is ever invoked.

## Automation Hints
- Framework: Playwright + pytest, per `.agents/testing.md`.
- Suggested location: new test method
  `test_import_skill_missing_frontmatter_shows_validation_error` in the
  existing `automation/tests/ui/skills/test_skill_export_import.py`
  (shares the Import flow's page objects/fixtures with ELITEA-1737/1738,
  but needs **no** `cleanup_skill_ids` fixture — nothing is created).
- **`SkillsListPage.import_skill()` is not reusable for this case as-is.**
  Its current implementation (`automation/pages/skills_list_page.py:561`)
  clicks Import, uploads the file, and then unconditionally calls
  `Dialog.wait_for(...)` expecting the "Import parameters" dialog — which
  will time out on an invalid file, since no dialog ever appears. Add a
  new page-object method (e.g. `upload_skill_file(file_path)`) that only
  does the click + file-chooser + upload steps and returns without
  waiting on the dialog, so both the valid-import tests (ELITEA-1737/1738,
  which then call `Dialog.wait_for` themselves or via the existing
  `import_skill()`) and this validation-error test can share the upload
  step without one forcing an assumption the other can't meet.
- Add the `toast_alert` / `TOAST_ALERT_SEVERITY` / `get_toast_alert()`
  trio to `SkillsListPage`, copying the existing `ChatPage`
  (`automation/pages/chat_page.py:965-972,1946-1955`) /
  `PipelineDetailPage` pattern verbatim — no new testid, this is pure
  page-object plumbing reuse.
- Assert the toast message via `.get_toast_alert("error")` scoped locator
  + reading its `toast-message` child text, rather than the unscoped
  `import_success_toast_message` field (which doesn't filter by
  severity) — add a severity-aware text-getter mirroring
  `ChatPage.get_toast_text()`.
- For the "no skill created" assertion, prefer `skill_api.list_skills()`
  before/after (session- or test-scoped `SkillAPI` fixture, same fixture
  already used for cleanup elsewhere in this suite) over parsing the
  "Skills: N" UI stat text — the API signal is exact or the UI text
  needs a new testid, and the network-absence check (no `skill_import`
  request) makes it a belt-and-suspenders assertion, not the sole one.
- Test fixture file: check in as
  `test-data/skills/missing-name-frontmatter.md` (or similar, per
  `test-data/` convention in `.agents/testing.md` § Test data strategy)
  rather than generating it at runtime — it's a static, purpose-built
  invalid file with no dependency on any other test's state.
- Wait strategy: wait for `toast_alert` (or the severity-scoped variant)
  to become visible rather than a fixed sleep — the toast in this run
  appeared well within the framework's default 10s UI element timeout
  and auto-dismissed on its own after a few seconds (default `toastError`
  duration), so assert while it's visible rather than racing the
  auto-hide.
