## Known Defects Found During Exploration

**No functional product defect found.** Two gaps and one non-issue to record:

1. **[Non-blocking, informational — not a defect] The base `POST /applications` response body's `version_details.tools: []` can look like a failed attachment if read in isolation.** Root-caused via network-log sequencing (step 5): the create call and the two association PATCHes are three separate requests fired in sequence (`createApplication` → `associateToolkits` → `associateApplications`, all `await`ed sequentially per `GenerateAgentModal.jsx`'s `handleApprove`-equivalent flow, source-read). This is by design (the base agent must exist before it can be an `entity_id`/`entity_version_id` target for the association calls) — not filed, documented here purely so a future implementer doesn't misread the create response as evidence of a broken attachment.

2. **[Clarification — filed] Case ELITEA-1909's stated preconditions never establish how to make an existing Agent suggestible (step 4/8's prerequisite).** Filed as a GitHub issue labelled `question` in `EliteaAI/elitea-testing-public`, noting "Found while working #102" per this case's own AFS-authoring instructions — the question: should ELITEA-1909's preconditions be updated to state "a GitHub-relevant Agent also exists in the project" (mirroring the toolkit precondition), given the suggestion engine (confirmed live, matches ELITEA-1907's finding) only surfaces existing project resources filtered by prompt relevance? This AFS's own Preconditions section documents the verified answer and the AFS proceeds as `ready-for-automation` rather than blocking, but the case's source-of-truth text should be corrected so future analysts don't have to re-derive this.

3. **[Not a defect — pre-existing tooling quirk, ruled out during exploration, not filed]** `AgentAPI.create_agent()`'s default `llm_settings` payload (`temperature: 0.6` + `reasoning_effort: "medium"` together) is rejected by the live API with `400` (`"temperature is not allowed together with a reasoning_effort (other than 'none')"`) for whatever model this project's `default_model_name`/`default_model_project_id` currently resolve to. Worked around in this run via `AgentAPI.create_agent_full()` with `llm_settings` omitting `reasoning_effort`. This is a test-helper-vs-live-model-contract mismatch in `automation/api/client.py:366-405`'s convenience method, not a product defect — flagging for whoever next touches `create_agent()`, since any test relying on the convenience method against a reasoning-only default model will hit the same 400.
