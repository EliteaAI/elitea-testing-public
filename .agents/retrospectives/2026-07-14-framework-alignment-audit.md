# Framework Alignment Audit — 2026-07-14

Commissioned by the operator: review `.agents/`, execution logs, the obsolete
`ui-test-orchestrator` agent + its skill graph, `.claude/rules/`, and the
deliverables on both branches; confirm alignment with the framework architecture
and design — in particular the (newly revealed) goal: **data-testid everywhere,
UI-automation coverage measured via testids**.

Method: 6 parallel dimension audits, every critical/major finding independently
re-derived by an adversarial verifier. 49 agents, 43 findings verified: **42
confirmed, 1 refuted**. Read-only — nothing was modified.

## Executive verdict

**NOT aligned with the stated design intent.** The deliverables are real and the
mechanical process held, but the testid-everywhere/coverage goal is (a) recorded
in no document, (b) contradicted by at least six layers of the guidance stack,
and (c) invisible in the delivered code: the 12 cases merged 2026-07-14
contributed **zero** new testids, and 70% of page-object locator usage cannot be
seen by any testid-based coverage measurement. Separately, the tracker layer
misstates reality: all 12 merged cases are localhost-green-only, while the few
closure records that exist claim "fully promotable".

## Dimension verdicts

### agents-seed — **PARTIALLY_ALIGNED**

The .agents/ seed is internally coherent on its core mechanics — locator policy (testid-only, class fields), TMS adapter/intake (test-automation.yaml matches the wired onetest-tms MCP server, the intake dir, and real case frontmatter), and the fork retirement is propagated across all ten docs and four briefings (onboarding.md correctly marks the old topology as superseded; the fork-era CLAUDE.md text in the audit prompt is a stale snapshot, not the on-disk file). However, three major coherence defects remain. First, the newly revealed operator goal — data-testid everywhere, with UI-automation coverage measured by testid presence — appears in NO document; every doc frames testids as reactive per-case leaf additions, which actively steers against the goal; it should be seeded into testing.md § Locator strategy and workflow.md, with echoes in profile.md, architecture.md, and CLAUDE.md. Second, profile.md's board rule 'Done = PR merged, nothing else' and its bare '✅ done' comment convention contradict workflow.md's post-retirement closure-record rule (merged-but-unpromotable is blocked, issue stays open) — profile.md was never updated for the 2026-07-13 revision, while the lead briefing was. Third, AGENTS.md:65 still points readers at a 'locator ladder', a doc-level echo of the known SKILL.md root cause that keeps the fallback-hierarchy mental model alive in an always-read file. Reality-drift also exists on back-writes: 4 of 11 freshly merged cases were back-written with pytest node-id paths instead of the mandated dotted format, and an undocumented automation_pr field is being written.

### orchestrator-agent — **MISALIGNED**

The ui-test-orchestrator agent is a live, invocable competing pipeline: it is declared legacy only in .agents/team-comms.md while its own file still carries a broad auto-delegation trigger, and its 6-stage flow bypasses every current gate (no AFS, no manual execution, no fresh-session reviewer, no live-run merge gate, no closure record) and never even requires the test to run. Its skill graph is partially rotten on disk despite PR #23: page-object-generator — still load-bearing via .agents/workflow.md — instructs 'testid + fallback' in four places and 'testid even if not in frontend', add-data-testid retains a role/text 'fallback locator' edge case, the orchestrator's own checklist still says 'locator for legacy' (contradicting its PR-#23-fixed Stage 3), and test-quality-checker's bare-locator detection scans only test bodies, making the 12-PR failure mode (raw locators inside page-object methods) invisible to it. Notably, the current test-automation-workflow skill references none of the 7 skills, so the pipeline's only wiring to the testid machinery is .agents/workflow.md and memory briefings — consistent with 12 PRs creating zero testids. Of the 7 skills, add-data-testid, page-object-generator, and start-ui-localhost are load-bearing; test-scout, ui-test-creator, and test-deduplication are orphaned with the orchestrator; test-quality-checker hangs only off the equally-legacy failure-investigator. Recommendation: archive ui-test-orchestrator.md out of .claude/agents/ (do not update it — every stage already has a canonical owner in Tal's pipeline), with a deprecated-description rewrite as the minimum stopgap, and fix or retire the misaligned skill texts it leaves behind.

### rules — **MISALIGNED**

Post-PR-#23, page-objects.md is internally coherent and the 2026-07-13 chained-sub-locator anti-pattern plus its sign-off checklist items survived the merge intact — the merge even removed a lingering getByRole 'Locator Priority Order' ladder and a 'testid + fallback' checklist line that had contradicted the testid-only doctrine inside the rule file itself throughout the 12-PR authoring window. But the stack around that one file is misaligned on nearly every axis: mui-patterns.md, auto-applied to the identical paths, prescribes raw CSS, aria-label/get_by_role, css-* hash classes and bounding-box positioning wholesale, none of which fits page-objects.md's data-testid-constants-only scoped-selector exception, and it institutionalizes 'this panel has no testids' workarounds that directly defeat the new testid-everywhere coverage-measurement goal. The framework code diverges from the rules in both directions: locator_descriptor.py still accepts and its docstring actively recommends the forbidden locator= param (examples nearly identical to the rule's ❌ WRONG block, divergence undocumented anywhere outside a code comment), 13 descriptors in two live page objects still pass fallback= (dead code that comments falsely call 'the only strategy'), and 229 raw self.page.locator/get_by_* calls exist across 15 page files plus direct locators in 8 test files. The mandatory allure.step convention appears in zero of the five rules, and ui-tests.md's canonical test example omits it. Glob coverage was NOT the failure mode for the 12 PRs — every touched file was inside page-objects.md/ui-tests.md paths — though automation/fixtures/** and automation/components/** sit outside all globs. Finally, the test-automation-workflow skill never references .claude/rules/ at all, and add-data-testid's 'Element Not Found' edge case tells authors to fall back to role/text locators, keeping a non-testid escape hatch open.

### deliverables — **PARTIALLY_ALIGNED**

Deliverables are materially real: 12 PRs merged to automation/base (11 case PRs + the #24 ELITEA-1737 fix), each case shipped one test file with full 'Step N —' allure.step wrapping, an AFS exists for all 12 cases in test-specs/skills/, TMS back-write is done for all 11 (status: ready, execution_type: automated, valid automation_test_id), and EliteaUI is exactly in the designed post-fork state (automation/testids = main + only the 5 EL-1737 commits; #525/#526 open drafts; nothing local or unpushed). The tracker layer, however, does not tell the truth about this work: only 2 of 11 closed issues carry the mandated closure record (one not even as the last comment), issue #19 was closed in direct violation of the convention that cites it as its own worked example, and — worst — the promotability claims in the records that do exist (#35/#36/#37: 'fully promotable', 'no cross-repo testid dependency') are factually false. Ground truth is that ALL 12 cases are localhost-green-only: every test creates skills through SkillFormPage.fill_form, whose fill_instructions resolves 'skill-instructions-editor-content', a testid that exists only on automation/testids via still-draft EliteaUI PR #526 (with #525's skill-tags-input/skills-import-button adding a second blocker for 1737/1738/1740). Additionally, page objects carry 12 phantom testid descriptors that exist in no EliteaUI branch, and the TMS repo has case-ID collisions (1735/1736/1738/1740 duplicated across three directories) that will corrupt any testid/case-ID-based coverage measurement the team now plans. Verdict: the artifacts are aligned, the truth-tracking around them is not.

### coverage-readiness — **MISALIGNED**

Reality is far from the testid-everywhere goal on every axis, and no measurement infrastructure exists yet. EliteaUI main carries only 75 unique static data-testids against roughly 565 interactive MUI components (~13% density), and the whole automation effort has added just 3 — all from ELITEA-1737, all stranded in draft PRs #525/#526 so main has gained zero. On the framework side, 70% of the 514 locator usage points in automation/pages/ (351 raw/chained non-testid handles, 89% of all method-body handles) are invisible to testid-based measurement, 84 of 125 LocatorDescriptors still carry forbidden fallbacks (13 with no testid at all, where fallback is live code), and 54 referenced testids are not statically defined in the UI — 26 don't exist in the source at all, so the visible inventory is partly fiction. The onetest automation_coverage verb measures case-to-test correlation (automation_test_id ↔ code_ref), not element coverage; nothing testid-based exists or is designed. Bottom line distortion: measured by testids today, the 12 merged cases score exactly 0 while one unfinished case (EL-1737) holds 100% of the signal — and even that signal is 0 against main. Auto-applied rules (mui-patterns.md) and the descriptor API itself still teach raw CSS/aria locators, so drift will continue until they are fixed.

### execution-logs — **PARTIALLY_ALIGNED**

Across the 12 lead (Tal) sessions of 2026-07-13/14, hard controls held but soft conventions decayed. Live-run merge gate: 7 of 11 work sessions ran a genuine >=3-consecutive-GREEN gate pre-merge; 2 violated it (30e159d9 claimed "GREEN 3/3" from ONE pytest invocation that passed 3 different tests; baf8f3cf merged first and ran the gate post-hoc, self-caught and logged to memory), and 2 merged deterministically-RED tests under a sanctioned-known-defect pattern (bba8bd9f ran no lead gate at all; a724d2fc ran 3/3 deterministic pre-merge). Verdict: the deterministic, mechanical rules (identity, board, squash-merge, TMS back-write) show 100% compliance while judgment-dependent gates (closure record, pre-work sync, gate semantics under known-defect RED) eroded exactly where the written convention is ambiguous or unenforced.
