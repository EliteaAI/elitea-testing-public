## Findings Applied

### 1. UI/flow assumption gate (User-identified)

**Evidence:** Multiple sessions (b9b71e12, ebae2583, 76bb064f, 14e06b31, d884c08c) showed thrash where agents assumed UI changes without verifying against the TMS case text.

**Problem:** When a test fails, agents would assume the product changed (e.g. "button moved", "wizard has extra step") and build fixes around that assumption, only to discover later the assumption was wrong. The case text is ground truth for intended behavior.

**Action:** Created curated entry for both `qa-engineer` and `test-automation-engineer`:
- `.agents/memory/qa-engineer/ui_flow_assumption_gate.md`
- `.agents/memory/test-automation-engineer/ui_flow_assumption_gate.md`
- Added index line to both roles' `MEMORY.md`

**The rule:** When you assume UI/flow changed → STOP → verify against the case text first → if unconfirmed, surface to user and wait for direction.

---

### 2. Backend API investigation discipline (User-identified)

**Evidence:** Session d884c08c + investigation files (`MCP_POOL_ANALYSIS.md`, `MCP_ISSUES_ANALYSIS.md`) — MCP 503 errors were initially misdiagnosed until proper isolation revealed pool saturation.

**Problem:** Backend API failures were not investigated systematically — missing the isolation step, the CI vs local comparison, and the retriability determination.

**Action:** Created curated entry for `test-automation-engineer`:
- `.agents/memory/test-automation-engineer/backend_api_investigation.md`
- Added index line to `MEMORY.md`

**The procedure:**
1. Isolate the API call (run outside test framework)
2. Compare CI vs local execution (identify env differences)
3. Determine retriability (503 temporarily_unavailable = YES, 4xx = NO)
4. Identify backend vs runner issue

Includes decision tree for when to rely on retry logic.
