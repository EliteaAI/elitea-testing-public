## ELITEA-1910 — split rewrite (live where possible, invariant where not)

The one observable genuinely unreachable live is the ≤5 cap itself — the
mock exists ONLY to prove a payload with >5 items would overflow the cap.
That specific probe cannot be produced by a live call (you can't ask the
live generator for exactly 7 skill suggestions on demand). Per the human's
own recipe: **write the invariant, don't fabricate the boundary. The "where
does the cap belong" question already has a human answer via #1317 — this
brief does not reopen that, only fixes what CAN be made live.**

1. Steps 1, 2, 3, 5, 6 rewrite exactly like ELITEA-1906 above: drop
   `modal.mock_generate_success(SUGGESTED_SKILLS_CAP_PROBE_PAYLOAD)`, use
   `modal.click_generate_and_wait_for_response(timeout=LIVE_GENERATE_RESPONSE_TIMEOUT)`,
   capture `body = response.json()`.
2. **Step 3** ("Suggested Skills" section present) — this needs the live
   response to actually include `suggested_skills`. `SUGGESTED_SKILLS_CAP_PROMPT_TEXT`
   ("An agent that uses several specialized skills to manage repository
   workflows") may or may not reliably surface a live Skill suggestion in
   project 400 — the AFS's own Preconditions flagged multi-category live
   suggestions as unreliable here. **If the live call does not return any
   `suggested_skills` for a reasonable prompt, this step (and 5/6 below)
   cannot be honestly rewritten live — stop and return this half as
   `blocked`, do not fabricate a workaround.** Try the prompt as-is first;
   only escalate to `blocked` if a real live attempt (not a guess) shows the
   category empty.
3. **Step 4 — the cap check.** Replace the fixed "did we mock >5, did we
   render >5" tautology with the invariant that WOULD catch a real violation:
   ```python
   rendered_count = modal.count_resource_items("skill")
   suggested_count = len(body["suggested_skills"])
   # Known defect: EliteaAI/elitea-testing-public#1317 — the invariant is
   # "never render more than 5", checked against however many the live
   # response actually suggested (could be fewer than 5, in which case the
   # cap simply never engages and this passes cleanly).
   if rendered_count != min(suggested_count, 5):
       soft_failures.append(
           "Known defect https://github.com/EliteaAI/elitea-testing-public/issues/1317: "
           f"expected min(suggested={suggested_count}, 5) rendered cards, got {rendered_count}"
       )
   ```
   Keep the `soft_failures` + trailing `pytest.fail()` pattern — unchanged,
   still sanctioned RED per `.agents/testing.md` § Merge gate (this specific
   assertion is still deterministic and single-cause; only its *comparison
   target* changed from a hardcoded 7 to whatever the live response actually
   returned).
4. **Steps 5-6** (sampled cards show correct name/description, unselected
   by default) — replace the hardcoded `(1, 4, 7)` id/name/description
   literals with a loop over whatever `body["suggested_skills"]` actually
   contains (e.g. sample first/middle/last of the REAL list, or all of them
   if the live count is small — your call, keep it proportionate). Compare
   against `item["name"]`/`item["description"]` from the response, not a
   hand-typed string.
5. Update the module docstring's ELITEA-1910 paragraph and the AFS
   (`test-specs/agents/lextend_build-with-ai-suggested-skills-section-shown-with-up-to-5-skills_ELITEA-1910.md`)
   the same way as ELITEA-1906 above — remove the UNDER REVIEW banner if the
   live half genuinely lands; if you had to return the Skills-section half
   as `blocked` (per point 2), say so explicitly in both the AFS and your
   Run Report instead of silently downgrading coverage.
