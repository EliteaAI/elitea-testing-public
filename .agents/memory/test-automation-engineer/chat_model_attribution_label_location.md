While implementing ELITEA-1881 (LLM selector Anthropic models), needed to assert
that a chat response is attributed to the correct model (e.g. "Anthropic Claude
4.5 Sonnet" shown for a response generated by that model, not a different one).

Two candidate DOM locations were confused at first:

1. **`ApplicationAnswer.jsx`'s `participantName` Typography** (header row, via
   `useParticipantName(participant)`) — this shows the **agent/participant
   name** (e.g. "Test Agent"), NOT the model name. Confirmed live: on the
   agent's own embedded chat, both the user's message and the AI response's
   header both render "Test Agent" here.

2. **`ApplicationThinkView.jsx`'s reasoning-step label**, inside the
   collapsible "Thought for Ns" trace accordion — THIS is where the model's
   display name actually renders (confirmed live via DOM inspection:
   `chat-message-item`'s `textContent` included `"...Thought for 2 secs
   Anthropic Claude 4.5 Sonnet CONFIRMED"`). No dedicated testid exists on
   this label — it's a plain `<span>` deep inside the reasoning-group
   rendering logic (`groupActions`/`ActionView`/`StreamingThinkBlocks`), not a
   simple leaf under a testid-carrying container.

**Handling used (not full remediation):** `AgentDetailPage.get_last_chat_message_full_text()`
reads the raw `text_content()` of the whole last `chat-message-item` `<li>`
and asserts the expected model's display name is a substring (and that OTHER
candidate models' names are NOT). This was a deliberate choice to honor the
ELITEA-1881 AFS's own disposition ("not remediated, flagging for a future
add-data-testid pass") rather than in-scope-remediating a non-trivial nested
trace element mid-case.

**For future work touching this area:** if a case needs a *stable, precise*
handle on the model-attribution label (not just substring containment), that
add-data-testid pass is still owed — the leaf `<span>` inside
`ApplicationThinkView.jsx`'s reasoning-group render needs its own testid
(something like `chat-message-model-attribution`), analogous to how
`ApplicationAnswer.jsx` already carries `chat-answer-content`/
`skill-test-last-response` on its own answer body. Don't assume
`participantName` is that handle — it isn't.
