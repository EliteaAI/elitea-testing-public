## Session 3: Claude Code hook additionalContext hard-caps at 10,000 chars — shared docs + role memory were silently not reaching context (RESOLVED)

Operator noticed the SessionStart hook's payload showed up as a truncated
`<persisted-output>` in the transcript and asked why. Root cause, verified
three independent ways (docs, live transcript, execution):

- **Doc-verified** (code.claude.com/docs/en/hooks): "Hook output strings,
  including `additionalContext`... are capped at 10,000 characters. Output
  that exceeds this limit is saved to a file and replaced with a preview and
  file path." This is a Claude Code platform limit, not Copilot-specific.
- **`lib.sh` bug**: `.claude/hooks/sdlc-skills/lib.sh`'s `build_capped_context`
  has a branch `if [ -z "${COPILOT_CLI:-}" ] && [ -z "${SDLC_VSCODE:-}" ]; then
  <inline everything, uncapped>; fi` with a comment claiming "the cap is
  Copilot-specific; other runtimes (Claude/Codex/Cursor) inline as-is" — false
  for Claude Code per the docs above. Upstream bug (arozumenko/sdlc-skills),
  not reported upstream this session — flagged here only.
- **Transcript-verified** (this session's own `.jsonl`): a `hook_success`
  record shows the hook emitted a correct, full 75.7KB `additionalContext`
  (role memory + 6 `SDLC_SHARED_DOCS` docs concatenated); the very next
  record, `hook_additional_context`, shows Claude Code swapping it for the
  `<persisted-output>...Preview (first 2KB)...` wrapper — textbook match for
  the documented over-cap behavior, not a crash.
- Comparison: `obra/superpowers`'s own `session-start` hook injects one file
  (`using-superpowers/SKILL.md`, 3,063 bytes) — it "works" only because it
  never gets close to the cap, not because of any smarter handling.

**Fix 1 — shared docs moved off the hook, onto CLAUDE.md `@import`** (confirmed
via `code.claude.com/docs/en/memory` + `/docs/en/sub-agents`):
`@path` imports in the PROJECT-ROOT CLAUDE.md are (a) uncapped — a hook-only
limit, doesn't apply to CLAUDE.md loading; (b) delivered to EVERY dispatched
subagent, not just the top-level session — confirmed: "A non-fork subagent's
initial context contains... CLAUDE.md files: every level of the CLAUDE.md
hierarchy the main conversation loads... including project rules"; (c)
compaction-resilient — "What survives compaction" table: "Project-root
CLAUDE.md and unscoped rules → Re-injected from disk" (live re-read + re-expand,
not a frozen snapshot), unlike `SubagentStart`'s injection which has NO
equivalent refire-on-that-subagent's-own-compaction path. Net: CLAUDE.md
imports are strictly more robust than the hook channel for anything not
role-specific. Added all 8 root `.agents/*` docs (not just the hook's 6 —
also `architecture.md` + `test-automation.yaml`, which the hook never
covered at all) as literal `@.agents/<name>` lines (not backticked/fenced —
import parsing skips code spans) in CLAUDE.md's "Team & Way of Work" section.

**Fix 2 — stopped the hook from also inlining shared docs (so role memory
survives on its own):** `shared_doc_names()` in `lib.sh` reads
`${SDLC_SHARED_DOCS:-$SDLC_SHARED_DOCS_DEFAULT}` — bash's colon-dash form
treats EMPTY same as UNSET, so setting `SDLC_SHARED_DOCS=""` in `config.sh`
(the sync-safe override file) does NOT suppress it — it silently falls back
to the same 6-doc default. Only a non-empty sentinel that matches no real
file works: `: "${SDLC_SHARED_DOCS:=__none__}"`. Verified live by sourcing
`lib.sh` directly and calling `build_capped_context "$(pwd)" "scout" "" ""` —
dropped from 75.7KB to 6,138 bytes (role memory only), comfortably under
10K. User applied the config.sh edit; I verified it by execution, not just
reading it.

roles):** even with shared docs removed, 3 of 4 roles' OWN `MEMORY.md` index
already exceeds the real per-role hook budget
(`10000 - project_briefing.md - snapshot.md - ~250` header bytes) purely

Claude Code's OWN native auto-memory (a different, unrelated mechanism —

guard that nudges-then-errors; this project's `.agents/memory/<role>/`
